### Раздел 2. Процессные протоколы

#### 1. Правила ветвления в Git (GitHub Flow)
Основная ветка: `main` (всегда стабильна, прямой push запрещён правилом защиты ветки).
Пример наименования ветки под задачу: `feature/DEAN-21-gpa-calculator`
Другие шаблоны имён: `feature/DEAN-<номер>-<кратко-латиницей>` — новая функциональность (`feature/DEAN-22-academic-scholarship`); `bugfix/DEAN-<номер>-<описание>` — исправление дефекта (`bugfix/BUG-42-gpa-retake`); имена только в нижнем регистре, через дефис, с номером задачи из бэклога.
Условие создания Pull Request для нового модуля: модуль собирается без ошибок и предупреждений, к нему написаны xUnit-тесты (ядро расчёта GPA/стипендий покрыто не менее чем на 80 %), обновлена спецификация `dean-grades-api.yaml`, ветка обновлена от свежего `main`; заголовок PR — `DEAN-21: Расчёт GPA за семестр`, в описании — ссылка на задачу и способ проверки.
Правило слияния: PR одобряется минимум 1 коллегой после успешного прохождения автоматических тестов (GitHub Actions: build + `dotnet test`); слияние — Squash merge, после слияния ветка удаляется.

#### 2. Чек-лист Code Review (3 обязательных пункта)
1. **Корректность бизнес-правил деканата:** расчёт GPA и стипендий соответствует Положению (средневзвешенный балл по зачётным единицам, округление до 2 знаков, учитывается итоговая оценка после пересдачи, зачёты «зачтено/не зачтено» не входят в GPA); на граничные случаи есть xUnit-тесты, и они проходят.
2. **Защита персональных данных и прав доступа (152-ФЗ):** ФИО, номера зачёток и оценки студентов не пишутся в логи и тексты исключений; эндпоинты проверяют роль (`Dean`, `Methodist`, `Student` — студент видит только свои оценки); изменения оценок и приказов фиксируются в журнале аудита.
3. **Соответствие контракту и стандартам кода:** DTO, маршруты и коды ответов совпадают с `dean-grades-api.yaml`; нет «магических чисел» (пороги стипендии и суммы — в конфигурации/таблице политики); имена по C# Coding Conventions; асинхронные методы с `CancellationToken`; решение собирается без предупреждений.

### Раздел 3. Запись архитектурного решения (ADR-001)

Заголовок: ADR-001: Выбор паттерна «Стратегия» (Strategy) с версионируемыми правилами для модуля расчёта стипендий
Статус: Принято (24.10.2026)
Контекст и проблема: Правила назначения стипендий в деканате (академическая, повышенная академическая, социальная) и пороги среднего балла ежегодно меняются приказом ректора. Если зашить их в код условиями `if/else`, каждое изменение Положения требует нового релиза, а пересчёт прошлых семестров начнёт выполняться по новым правилам — приказы прошлых лет перестанут совпадать с данными системы. Кроме того, разные виды стипендий проверяются по разным критериям, и метод расчёта разрастается.
Принятое решение: Каждый вид стипендии реализуется отдельной стратегией за интерфейсом `IScholarshipRule` (`AcademicScholarshipRule`, `IncreasedScholarshipRule`, `SocialScholarshipRule`); `ScholarshipCalculator` получает набор стратегий через DI. Числовые параметры (пороги GPA, суммы, допустимость оценки «3») хранятся в таблице `ScholarshipPolicy` с датами начала/окончания действия, а в проекте приказа сохраняется номер версии политики. Новое правило = новый класс + запись в таблице, без изменения существующего кода (принцип открытости/закрытости), каждая стратегия тестируется отдельно xUnit-тестами.
Отклонённая альтернатива и причина: 1) Условия `if/else`/`switch` в одном сервисе — отклонено: нарушает OCP, растёт сложность метода, нет истории версий правил, нельзя корректно пересчитать прошлый семестр. 2) Подключение движка бизнес-правил (NRules / Drools) — отклонено: для 3–5 правил это избыточная зависимость, правила в DSL сложнее покрывать модульными тестами и проверять на Code Review, у команды нет опыта сопровождения такого движка.
Последствия: + изменения Положения вносятся без релиза (новая версия политики); + прозрачная история «по каким правилам выдан приказ»; − нужно поддерживать таблицу политик и миграции к ней.
